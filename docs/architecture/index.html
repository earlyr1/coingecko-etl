CoinGecko ETL

The pipeline polls CoinGecko every 30 seconds and keeps every API call in Postgres before any deduplication. It moves raw JSONL through an S3 lake and Redpanda, and writes cleaned, normalized snapshots to the processed zone exactly once, even when a step crashes and runs again.

4 zonesraw, processed, rejected and dlq (dead-letter: records a stage could not process), as plain files

One snapshot, end to end

Three polls of /coins/markets travel through the pipeline. Poll B got the same cached bytes as poll A; poll C carries the next snapshot. Prices, timestamps, cache headers and payload hashes come from those recordings, which asked for the top 10 coins (per_page=10) to keep them short; the pipeline asks for 100. Ids, sequence numbers and offsets are illustrative. For brevity, all three polls and the bitcoin /coins/{id} call between them travel in one export batch and one consumer batch, as after a short stall. At the normal cadence (export every 15 s, fetch wait 5 s) each call travels alone, and the deduplication decisions are the same.

    Time model

    An event is a source snapshot. About every 60 seconds CoinGecko recomputes its coins in one pass and gives every recomputed coin the same last_updated; a coin it skips keeps its older stamp. snapshot_at is the newest stamp in a response. Pick a scenario to see which times exist and which one becomes the event time.

      FieldSourceMeaning
      snapshot_atDerived: max last_updated in a markets response; the document's last_updated for /coins/{id}When CoinGecko assembled the snapshot. Event time, part of every natural key, and the partition date.
      source_updated_atAPI last_updated of the coinWhen CoinGecko last recomputed this coin. Lags snapshot_at by hours for stale coins.
      fetched_atOurs, in raw.api_callsWhen we polled. Lineage: reachable from any processed row through _event_id.
      last_traded_at, last_fetch_atAPI, tickers onlyLast trade on the exchange; when CoinGecko fetched the exchange's data.

      Data model

      One /coins/{id} document becomes a parent row and three child datasets: maps keyed by currency turn into rows, arrays and maps of objects become child tables. Select a dataset to see its columns. Counts such as 223 of 250 come from a top-250 sample taken on 2026-10-10.

      Normalize every row

      • "" and [] become null. CoinGecko marks a missing value four ways: null, "", [] or no key at all.
      • Timestamps become RFC 3339 UTC with milliseconds: 2026-10-10T10:07:55.000Z. genesis_date stays a date.
      • Money and quantities become decimal strings, never float64. Values pass 253: bitcoin's market cap in VND is "43083803721443304".
      • Symbols upper-case, EVM addresses lower-case. roi (null in 223 of 250 rows) flattens to roi_times, roi_currency, roi_pct.
      • Dropped as unneeded: images, descriptions, links, sparklines, trade_url, token_info_url and duplicated fields such as coin_mcap_usd.

      Reject to rejected/

      • missing_id: no coin id.
      • null_price, nonpositive_price.
      • empty_platform: bitcoin ships platforms: {"": ""}.
      • empty_record: every metric is null.
      • snapshot_conflict: same natural key, different content.

      Flag and keep

      • is_stale: snapshot_at − source_updated_at > 10 min; tickers: the upstream flag or a last trade older than 1 h.
      • is_inactive: zero volume (14 coins in the top 250, mostly tokenized money-market and bond funds).
      • is_anomaly: price outside [low_24h, high_24h] (3 coins in the top 250); tickers: the upstream flag or more than 2% from the coin's median.
      • Thresholds are configuration: ETL_STALE_AFTER, ETL_TICKER_STALE_AFTER, ETL_TICKER_ANOMALY_PCT.

      Delivery guarantees

      Every hop is at-least-once. The processed zone still holds each record once, because every step can run again safely: deterministic keys, ledgers in Postgres and write-once objects. Deduplication happens once, in the transformer; idempotency happens at every write.

      HopMechanismIf the step runs again
      fetcher → api_callsPrimary key (event_id, fetched_at), ON CONFLICT DO NOTHINGNo row is inserted twice. A crash before the commit loses one poll, visible in metrics.
      exporter → raw/xid8 cursor and the export_batches ledger; PUT with If-None-Match: *Same object, byte for byte: a 412 with an equal checksum counts as done.
      publisher → topicLease from the ledger; idempotent producer, acks=allThe batch is published again with the same event_ids; the transformer drops the copies.
      transformer → processed/Batch manifest, deduplication claims, write-once objects, offset commit after the writeSame decisions and the same bytes: a 412 with an equal checksum.

      Deduplication decision

      Each record claims its natural key in pipeline.dedup_claims; the first claim wins. Choose what arrived to compare it with the stored claim. Ids and offsets are illustrative.

      Topic partitions

      Redpanda speaks the Kafka protocol, so Kafka terms apply. Partitions give ordering and parallelism; they do not split traffic by endpoint. The producer hashes each message key with murmur2 (Kafka's default partitioner), so every repeat of the same data lands on the same partition and deduplication sees it in offset order.

      Six partitions, five keys and two consumers using the cooperative-sticky assignor, which moves only the partitions that change owner during a rebalance (one possible assignment shown). bitcoin hashes to the same partition as coins_markets, so only four partitions get data and at most four consumers can be busy. To scale out, publish one message per coin, which gives 100 keys.

      Transformer batch and crash points

      One in-flight batch per partition: a contiguous offset range [F..L]. Select a crash point to see what is left behind and how the next owner recovers.

      The naive rule drops every record whose key is already claimed.

      Schemas

      JSON Schema 2020-12 files live in schemas/, are embedded into the binary with go:embed and validated with santhosh-tekuri/jsonschema/v6. The major version sits in the file name, the $id, schema_version on every record and the v= path segment of processed data.

      S0 · source response
      source/coingecko/coins_markets.v1.json, coin.v1.json

      Permissive: only fields the transform reads are required and typed; extra fields pass, and nulls are allowed where observed. CoinGecko stopped returning community_data and developer_data on 2026-08-28; drift must not stop the pipeline.

      checked in the transformer
      S1 · raw event
      pipeline/raw_event.v1.json

      Strict. One API call: the api_calls row, the raw JSONL line and the message value are the same bytes. outcome = ok requires a payload, its sha256 and an idempotency key.

      fetcher · exporter · publisher · transformer
      S2 · processed row
      processed/<dataset>.v1.json

      Strict, one per dataset, including the _ lineage columns. A row that fails never reaches processed/.

      transformer output
      S3 · rejected and dlq records
      pipeline/rejected_record.v1.json, dlq_record.v1.json

      Strict. One dlq record shape for every stage. error_class is checked against a regex rather than a fixed list, so a new class needs no schema change and is still safe as a metric label.

      all writers of rejected and dlq
      StageChecksOn failure
      fetcher, before INSERTS1 envelope only; the payload is not inspectedNot inserted. ERROR log and etl_schema_validations_total{stage="fetch",result="fail"}: this is our bug. No dedicated alert; if it persists, the stale-data alert fires.
      exporter, publisherS1 per linedlq stage export or publish; the line is not passed on.
      transformer, inputstrict JSON, S1, sha256(payload) = payload_sha256, then S0dlq decode_error, schema_violation, integrity_error, source_schema_violation, or transform_error when a payload passes S0 but cannot be transformed. After a schema fix, raw objects are republished.
      transformer, outputS2 per rowdlq output_schema_violation; never written to processed.
      writing rejected or dlqS3 (rejected or dlq record schema)ERROR log with the original bytes in base64.

      Rollout of a compatible schema change: the transformer first, then publisher, exporter and fetcher. CI checks that the new version still accepts every fixture of the previous one. A breaking change gets v2 files, handled side by side in the same topic by dispatching on schema_version.

      Storage

      versitygw serves ./data over the S3 API; every bucket is a directory and every object a plain file, so cat works on the host. Postgres holds the raw call log and the pipeline state. Select a file to see a line from it; ids, batch numbers and offsets are illustrative.

      export+batch+<20-digit batch_id>.jsonl and publish+batch+<20-digit batch_id>.jsonl, one object per batch. stage=transform/ holds the transform_input and transform_output records of one consumer batch.
      .s3meta/ · versitygw sidecar metadata (gitignored)
      logs/ · <service>/etl.log, <container id>/transformer/etl.log
      Postgres tableHoldsRetention
      raw.api_callsEvery HTTP call with the response body as json (byte-exact), partitioned daily by fetched_at.Never dropped by the pipeline: failed calls are not exported and live only here. Production: drop old daily partitions with pg_partman.
      pipeline.export_batchesLedger of raw objects: row range, object key, checksum, export and publish status, publish lease.Not pruned; the raw zone is append-only.
      pipeline.dedup_claimsFirst position, event_id, idempotency key and content hash per natural key, partitioned by event_date.At least 30 days, longer than the 7-day topic retention. Not pruned locally; production drops old partitions with pg_partman.
      pipeline.consumer_batchesManifest of transformer batches: offset range, object keys, checksums, counts, planned or written. An EXCLUDE constraint (Postgres rejects a row whose range overlaps an existing one) forbids overlapping offset ranges.At least 30 days (not pruned locally).

      Persistence: ./data, ./.s3meta and ./logs are bind mounts; Postgres and Redpanda keep their data in the named volumes pgdata and redpanda. make down keeps everything; docker compose down -v deletes the named volumes. Keep ./data and ./.s3meta together: the write-once check reads the stored sha256 from the sidecar. The README lists the same mounts as docker run -v commands.

      Alerts

      • No successful poll for more than 2 minutes.
      • Records appeared in dlq/.
      • More than 5% of responses fail S0 over 15 minutes: the upstream format changed.
      • Export lag above 5 minutes.
      • Consumer lag growing for 10 minutes.
      • Frequent 429 responses.

      Logs: log/slog JSON in UTC with service, stage, event_id and batch, written to logs/<service>/etl.log and stdout. The two transformer replicas share ./logs, so each writes logs/<container id>/transformer/etl.log and no file has two writers.
