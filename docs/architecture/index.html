About this data

Prices, headers and hashes come from recorded responses for the top 10 coins (per_page=10; the pipeline asks for 100). Ids and offsets are illustrative. For brevity all calls travel in one batch.

    Time model

    Event time is snapshot_at: when CoinGecko built the snapshot, not when we polled.

      Delivery guarantees

      At-least-once hops, exactly-once content: deterministic keys, Postgres ledgers, write-once objects.

      HopMechanismOn retry
      fetcher → api_callsprimary key, ON CONFLICT DO NOTHINGno duplicate rows
      exporter → raw/xid8 cursor, ledger, If-None-Matchsame object, 412
      publisher → topiclease, idempotent producercopies dropped downstream
      transformer → processed/manifest, claims, write-oncesame bytes, 412

      Deduplication

      The first claim of a natural key wins. Pick what arrived.

      Partitions

      Same key, same partition: repeats are judged in offset order.

      5 keys land on 4 partitions, so at most 4 consumers are busy. Assignment shown is one possibility.

      Crash points

      One in-flight batch per partition. Pick a crash point.

      naive: drop every key already claimed

      Scroll sideways for C3, C4 and Z.

      C2–C4 and Z each have an integration test (testcontainers).

      Schemas

      JSON Schema 2020-12, embedded in the binary, checked at every hop.

      S0 · source response
      source/coingecko/*.v1.json

      Permissive: tolerates upstream drift.

      S1 · raw event
      pipeline/raw_event.v1.json

      Strict: same bytes in Postgres, raw and the topic.

      S2 · processed row
      processed/<dataset>.v1.json

      Strict: failing rows never reach processed.

      S3 · rejected and dlq
      pipeline/*_record.v1.json

      Strict: one record shape for every stage.

      StageChecksOn failure
      fetcherS1 envelopenot inserted · ERROR · metric
      exporter, publisherS1 per linedlq
      transformer inJSON · S1 · checksum · S0dlq
      transformer outS2dlq

      Compatible change: consumers first, then producers. Breaking change: v2 side by side.

      Alerts

      • no successful poll for 2 min
      • records in dlq/
      • > 5% fail S0 over 15 min
      • export lag > 5 min
      • consumer lag growing 10 min
      • frequent 429s
      What each metric means
      • etl_schema_validations_total{stage,schema,result} pass or fail per stage; drives the source-schema alert
      • etl_schema_violations_total{stage,schema,keyword} which JSON Schema keyword failed
      • etl_api_requests_total{endpoint,status} calls by result; 429 and 5xx stand out
      • etl_last_success_timestamp_seconds{endpoint} drives the stale-data alert
      • etl_source_data_age_seconds{endpoint} how old CoinGecko's data was when fetched
      • etl_export_lag_seconds age of the oldest unexported row
      • etl_s3_put_total{result} created, exists (412), mismatch, error
      • etl_records_total{dataset,outcome} written, duplicate, rejected, dlq
      • etl_dedup_dropped_total{reason} replay, duplicate_response, duplicate_record
      • etl_consumer_lag_records{partition} messages waiting per partition
      • etl_e2e_latency_seconds poll to processed
      • /healthz, /readyz, /metrics on :8080 in every long-running service

      Logs: slog JSON in UTC → logs/<service>/etl.log and stdout; each transformer replica writes its own file.
