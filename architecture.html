CoinGecko ETL

Polls CoinGecko every 30 s, keeps every call in Postgres, exports it in 5-minute windows to an S3 lake, publishes each window to Redpanda on a schedule, and writes each cleaned record to processed exactly once.

About this data

Prices, headers and hashes come from recorded responses for the top 10 coins (per_page=10; the pipeline asks for 100). Ids, offsets and partitions are illustrative.

    Time model

    Event time is snapshot_at: when CoinGecko built the snapshot, not when we polled.

      Data model

      One coin document → a parent row and three child datasets. Click a dataset.

      Delivery guarantees

      At-least-once hops, exactly-once content: deterministic keys, Postgres ledgers, write-once objects.

      Deduplication

      The first claim of a natural key wins. Pick what arrived.

      Partitions

      Messages are keyed by the event's idempotency_key. Assignment shown is one possibility.

      Each response has its own key, so all 6 partitions carry data; copies of one response share a key and a partition and are judged in offset order.

      Transformer batch and crash points

      C2–C4 and Z each have an integration test (testcontainers).

      Schemas

      JSON Schema 2020-12, embedded in the binary, checked at every hop.

      Schema evolution

      Compatible change: consumers first, then producers. Breaking change: v2 side by side, dispatched on the version inside each message. Cleaning-rule drops are not schema failures: they go to rejected/.

      Persistence and reset

      Bind mounts ./data, ./.s3meta, ./logs · named volumes pgdata, redpanda, cronicle, pushgateway, prometheus, grafana. make clean wipes everything but .env. ETL_WINDOW is fixed for the lifetime of a stack: the exporter refuses a ledger or a kept lake of another size, so a new size takes make clean. Object names carry no database or broker counters, so the lake may be kept when the stack is recreated with the same ETL_WINDOW (windows the old stack had not published are then published by hand). In production raw.api_calls would get pg_partman retention.

      What each metric means
      etl_schema_validations_total{stage,schema,result}
      pass or fail per stage; drives the source-schema alert
      etl_schema_violations_total{stage,schema,keyword}
      which JSON Schema keyword failed
      etl_api_requests_total{endpoint,status}
      calls by result; 429 and 5xx stand out
      etl_api_request_duration_seconds{endpoint}
      latency of calls that got a complete HTTP response, body read included; p50 and p95 on the dashboard
      etl_last_success_timestamp_seconds{endpoint}
      drives the stale-data alert
      etl_source_data_age_seconds{endpoint}
      how old CoinGecko's data was when fetched
      etl_export_lag_seconds
      seconds past the end of the oldest window not yet closed (0 on schedule)
      etl_s3_put_total{result}
      created, exists (412), mismatch, error
      etl_records_total{dataset,outcome}
      written, duplicate, rejected, dlq
      etl_dedup_dropped_total{reason}
      replay (same event), duplicate_response (same response), duplicate_record (same content, another response)
      etl_consumer_lag_records{partition}
      messages waiting per partition
      etl_e2e_latency_seconds
      poll to processed
      etl_job_last_success_timestamp_seconds{job}
      pushed by each Cronicle job on success; drives ETLPublisherStale and the maintenance alerts
      etl_job_last_run_timestamp_seconds{job}
      pushed by every run, failed ones too; next to the last success it tells a job that runs and fails from one that does not run
      etl_publish_records
      records the last successful publish run sent; etl_publish_dlq_lines the lines it sent to dlq
